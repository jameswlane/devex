# Applications Configuration

Store one application per YAML file under `applications/<category>/<app>.yaml`. Init writes the shipped catalog here:

```text
~/.local/share/devex/config/applications/
├── development/git.yaml
├── databases/postgresql.yaml
└── optional/
```

Personal overrides use the same tree under `$DEVEX_CONFIG_DIR/config/applications/` (normally `~/.config/devex/config/applications/`). See [configuration priority](/configuration#configuration-priority) for team and environment overrides.

## Application definition

Each file contains an application at the root, without an `applications:` wrapper:

```yaml
# applications/development/git.yaml
name: git
description: A distributed version control system
category: Dependency
default: true
linux:
  install_method: apt
  install_command: git
  uninstall_command: git
macos:
  install_method: brew
  install_command: git
  uninstall_command: git
windows:
  install_method: winget
  install_command: Git.Git
  uninstall_command: Git.Git
```

`name` identifies the application. `description` is required by validation. `category` is a display and filtering label; it does not need to match the directory name. `default` marks an application for default selection. `linux`, `macos`, and `windows` contain platform-specific installation settings.

For tools installed the same way on every platform, use `all_platforms`:

```yaml
# applications/development/example-tool.yaml
name: example-tool
description: Example tool managed by mise
category: Development Tools
default: false
all_platforms:
  install_method: mise
  install_command: example-tool@latest
  uninstall_command: example-tool
```

An OS configuration can also define `dependencies`, `pre_install`, `post_install`, `config_files`, `themes`, `download_url`, `destination`, and alternative installation configurations. Follow a shipped application with the same installer when adding these fields.

## Custom install hooks

`pre_install` and `post_install` accept explicit `shell` scripts. Treat application YAML and any referenced scripts as trusted executable code: command validation is a pattern-based policy, not a shell sandbox. Both interactive and noninteractive installation validate the original script with the configured security level, global overrides, and the application's `app_overrides` before execution. A rejection names the application and points to `security.yaml`; review the hook first and use a narrowly scoped override only for code you trust.

```yaml
post_install:
  - shell: |
      printf '%s\n' "Configuring $USER"
      mkdir -p "$HOME/.config/example" && printf '%s\n' 'ready'
```

Each script is passed intact as one argument to `bash -c`. Quotes, pipes, redirections, compound commands, globs, and command substitutions follow Bash rules. Variables expand in Bash at execution time, respecting single quotes and escapes; DevEx does not substitute environment values into script text beforehand. Quote variable expansions when they should remain one argument.

Hooks default to `scope: user`, using the original invoking account (including when DevEx was launched with sudo). The SDK passes the target username separately from the script and supplies that account's environment when switching users. `scope: system` must be explicit and contain only a shell script; it runs elevated, retaining shell variables and exposing the invoking username through `DEVEX_INVOKING_USER`. Quote it as `"$DEVEX_INVOKING_USER"`. Embedded `sudo` calls run noninteractively and require prior authorization.

Use the declarative `shell_init` and `path` actions for shell startup configuration. Their behavior is unchanged; they do not evaluate shell text during installation.

## Overrides

A higher-priority application with the same case-insensitive `name` replaces the whole lower-priority definition, including its platform blocks. Include every platform you want the override to support. Changing the filename or category does not create a separate application with that name.

```bash
devex list available
devex list available --search git
devex config validate
devex config edit applications
```

The editor opens every nested application YAML file in the default configuration directory. For a personal override, edit its file under `$DEVEX_CONFIG_DIR/config/applications/` (normally `~/.config/devex/config/applications/`) directly.

## Migrating legacy applications

`applications.yaml` and the older grouped files such as `terminal.yaml` still load with a deprecation warning. For each entry, create a separate application file and remove the legacy list/category wrapper. Convert flat `install_method` and `install_command` fields to an appropriate platform block or `all_platforms` block. Remove the legacy entry after verifying the new file with `devex config validate` and `devex list available`.

## Application configuration files

Add `config_files` to the selected platform block (or `all_platforms`). Each entry copies one regular file:

```yaml
linux:
  install_method: apt
  install_command: neovim
  config_files:
    - source: ~/.local/share/devex/assets/defaults/neovim/init.vim
      destination: ${HOME}/.config/nvim/init.vim
```

Both plain and TUI installation use this order: pre-install hooks, package installation, **configuration file copies**, then post-install hooks. The TUI also resolves dependencies before installing the package. Post-install hooks can read the copied files.

Paths support `~/`, `$HOME`, `$VAR`, `${VAR}`, and Windows-style `%VAR%` environment variables, including `%LOCALAPPDATA%`. Variables must be set and nonempty. Relative sources resolve from the CLI's working directory. Destinations must be absolute after expansion and stay inside the current `$HOME`; the schema does not grant exceptions for system paths. Traversal segments (`..`), symlinks at the destination, directories in place of files, and symlink escapes outside the home directory are rejected. Missing parent directories are created with user-only access, and copied files use mode `0600`.

An existing destination is moved to a sibling named `<destination>.<UTC timestamp>.devex-bak` before replacement. Backups remain available after uninstall. Successful copies, their content hashes, backup paths, and mapping warnings are recorded per application in `~/.local/state/devex/config-files/<application-name-hash>.json`. Uninstall removes only recorded copies whose contents still match; user edits and untracked files are preserved. `--keep-config` preserves the managed copies as well.

A failed mapping produces a warning with the application name, source, destination, and cause. Installation continues with the remaining mappings and post-install hooks, and the warning is saved in the configuration-stage result. TUI batch results also include these warnings. This policy does not undo a successfully installed package. If the result record cannot be opened, configuration copies are skipped with a warning.

`devex install --dry-run` prints the planned copy, parent-directory creation, and timestamped backup operations without writing files or changing the result record. It reports invalid mappings, but cannot predict every permission error that may occur when the actual installation writes files.

## Consent rules for app and plugin authors

Every effect must belong to an explicit user choice or a visible default that
can be disabled. Confirmation and `--dry-run` must show packages, dependencies,
package-list updates, shell-file edits, and desktop settings before execution.
Build the preview and execution from the same plan; do not hide extra tools in
post-install hooks. Already-installed applications must be skipped and reported.

Post-install hooks must stay within the selected application's scope. Use
`post_install` declarative `shell_init` and `path` actions for shell integration,
so DevEx targets the selected shell and backs up its managed changes. Raw
`>> ~/.zshrc` (and other shell rc appends) fail config validation. Do not use
other redirects, scripts, or commands to bypass that rule or change unrelated
applications, global preferences, or another shell's files. General shell
commands are not sandboxed: reviewers must check their write targets.

Optional aliases, history preferences, and desktop tweaks require an explicit
choice with visible defaults. GNOME and KDE plugins provide a side-effect-free
`describe` command: its JSON lists each native command's executable and exact
arguments for `configure`. Setup displays these settings at Confirmation,
disabled by default; press `s` to opt in. It passes the accepted plan's SHA-256
to `configure --expected-plan HASH`; a different plugin plan fails before any
setting is written. Plugins without a compatible preview are skipped. Automated
setup leaves desktop settings disabled. Setup saves the selected theme
preference without implicitly running a desktop plugin's `apply-theme` command.

Keep previews free of writes, package installation, session requirements, and
native-tool execution. When changing a desktop configure operation, update the
shared settings table used by both preview and execution. Test that the native
commands actually recorded during execution match the described commands, that
preview performs no writes, and that stale accepted plans fail before mutation.

Back up user files and settings before modifying them, preserve existing user
choices such as Git identity, and record enough information for restoration.
Report failures honestly, including partial changes; never label an incomplete
setup successful. Reviewers must verify scope, preview/execution parity,
reversibility, failure reporting, and regression coverage for every new effect.

## Registry catalog and offline use

`devex list available`, `devex install <app>`, and setup load application defaults
from `https://registry.devex.sh/api/v1/applications`. List search, category,
recommended, and output format options work on the resolved catalog. Applications
without an installation method for the current platform are excluded from the
available list. The CLI fetches all pages so local overrides participate in search
and filtering too.

The catalog is cached for one hour under the shared DevEx cache directory
(`$DEVEX_CACHE_DIR`, otherwise `$XDG_CACHE_HOME/devex`, normally `~/.cache/devex`).
Each registry URL has its own cache file. Stale single-page results use ETag
revalidation; paginated catalogs refresh all pages. Registry requests have a
five-second timeout and a fifteen-second budget for pagination.

If the registry fails, DevEx uses its last complete cached catalog, even if stale,
then the bundled application catalog. `--offline` or `DEVEX_OFFLINE=true` avoids
registry requests. DevEx reports stale-cache or bundled fallback and its reason on stderr. Fresh
registry responses and fresh caches are silent by default. `--verbose` always
reports the selected source, registry URL, cache age, and refresh or cache-write
errors. Installed listings, status, configuration, version, and help do not load
the registry catalog. JSON output
remains on stdout. Cache files can safely be deleted.

Local application definitions override registry, cached, or bundled defaults by
case-insensitive application name. A matching local definition replaces the whole
application, including platform methods; it is not a field-by-field merge. Local
tiers retain their existing precedence: default data config, its environment,
team config, its environment, user config, then its environment. Custom names are
added. Inline `applications` definitions from the selected configuration have the
highest precedence for installation.

To use a self-hosted registry, set:

```sh
export DEVEX_PLUGIN_REGISTRY_URL=https://registry.example.com
```

Or set `plugin_registry_url: https://registry.example.com` in
`$DEVEX_CONFIG_DIR/config.yaml` (normally `~/.config/devex/config.yaml`). The
environment variable takes precedence. Supply the registry origin; the CLI appends
`/api/v1/applications`. This setting is shared with plugin downloads.
