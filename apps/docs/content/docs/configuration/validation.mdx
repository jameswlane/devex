# Configuration Validation

```bash
devex config validate
devex config validate --strict
devex config validate --strict --format json
```

Loading, init, add, import and `config validate` use the same semantic validator.
Validation reads the runtime precedence stream: defaults, environment defaults,
team, team environment, user, and user environment. `DEVEX_ENV` selects the
active environment. Legacy files and canonical directory files use the same
precedence as loading; later application definitions replace earlier ones by name.
Optional absent tiers are valid.

## Modes and severity

Normal mode reports unknown schema keys as warnings. Strict mode promotes those
keys to errors. Both modes reject malformed YAML, invalid application structures,
unknown installation methods and cycles between known applications. Errors cause
a nonzero exit; mutations stop before destination files, backups or undo state
are written. Import prepares an isolated candidate configuration first. The
`--validate=false` flag is retained for compatibility; candidate semantic
validation always runs.

Init and add use normal mode, as does ordinary loading. Warnings do not block
these operations. Run strict validation in CI to prevent ignored fields from
entering shared configurations. For example, `dependencies` belongs inside an OS
configuration such as `linux.dependencies`; it is not an application root field.
Unknown fields include their file, field path, YAML line and column.

Installation methods are checked against the offline capability catalog, including
alternatives. A supported method does not require an already downloaded plugin
and validation never downloads one. Recognized planned methods produce `info` diagnostics:
the definition is valid, but that capability cannot execute until implemented.
Infos do not promise that every alternative can run on the current machine.

Dependencies matching known application names or package aliases participate in
cycle detection. A cycle diagnostic includes its path, for example
`A -> B -> A`. Unmatched dependencies produce `info` diagnostics and remain native package
names; validation does not attempt a network lookup or treat them as missing apps.
Platform requirements also refer to native packages.

## Diagnostics and file schemas

Application files contain one cross-platform application at the YAML root.
Environment language and shell entries also accept legacy application definitions.
Fonts, Git, global settings and desktop files each use their own typed schema.
SSH and terminal settings intentionally accept open maps. Unknown-key checks
also inspect nested structures and installation alternatives.

JSON output contains `valid`, `errors`, `warnings`, `infos` and `diagnostics`. Each diagnostic
includes `severity`, `category`, `message`, and source `file` and `field` when
available. Severity is `error`, `warning` or `info`. Warnings and infos do not
set `valid` to false, and infos are not counted as warnings. A JSON report is emitted before
the command returns its validation error.

`config show --detailed` reports file sizes and syntax status; use validation for
semantic checks. `--fix` currently reports that automatic fixes are unavailable;
correct the reported files manually.
