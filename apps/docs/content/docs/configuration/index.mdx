# Configuration

`devex init --profile backend --interactive=false` writes the configuration tree shipped with the CLI. The loader, `config show`, `config validate`, and `config edit` use this layout:

```text
~/.local/share/devex/config/
├── applications/
│   ├── development/git.yaml
│   ├── databases/postgresql.yaml
│   └── optional/
├── environments/
│   ├── programming-languages/go.yaml
│   ├── fonts/fira-code.yaml
│   └── shell/                         # Optional shell application definitions
├── system/
│   ├── git.yaml
│   └── global.yaml
├── desktop/
│   └── gnome/
│       ├── themes/themes.yaml
│       ├── settings/settings.yaml
│       ├── extensions/extensions.yaml
│       └── dock/dock.yaml
├── dotfiles.yaml
├── security.yaml
└── devex.yaml                         # Init metadata, not application definitions
```

Files under `applications/` contain one cross-platform application at the YAML root. Environment files contain one language, font, or shell definition. System and desktop files contain setting groups. YAML files in nested directories are read in alphabetical path order.

See [applications](/configuration/applications), [environment](/configuration/environment), [system](/configuration/system), and [desktop](/configuration/desktop) for file examples.

## Configuration priority

Configuration tiers load from lowest to highest priority:

1. Defaults: `~/.local/share/devex/config/`
2. Default environment: `~/.local/share/devex/config/environments/<env>/`
3. Team: `$DEVEX_TEAM_CONFIG_DIR`, or `~/.devex/team/`
4. Team environment: `<team>/environments/<env>/`
5. User: `~/.devex/config/`
6. User environment: `~/.devex/config/environments/<env>/`

The environment is selected from `DEVEX_ENV`, then `ENVIRONMENT`, then `NODE_ENV`, with `dev` as the fallback. Every tier uses the same directory layout. For example, a personal Git override goes in `~/.devex/config/applications/development/git.yaml`.

Applications with the same case-insensitive `name` replace the lower-priority definition as a whole. The filename and category do not determine identity. A higher tier wins whether it uses a directory file or a supported legacy file. Within one tier, directory definitions override legacy definitions. Prefer one definition per application per tier.

## Initialize and inspect

```bash
devex init --profile backend --interactive=false
devex list available
devex list available --search docker
devex config show --detailed
devex config validate
devex config edit applications
```

Init fills in missing shipped files and preserves existing files. `devex.yaml` records profile and initialization choices; application definitions live under `applications/`.

`config show` summarizes the default tree, including nested YAML sizes and syntax errors. `config validate` checks nested YAML and application content. `config edit environment` opens the files under `environments/`; `config edit all` also includes existing `dotfiles.yaml` and `security.yaml`. These commands operate on the default configuration directory; put personal or team overrides in the corresponding tier when editing those tiers directly.

## Legacy files

Existing monolithic files continue to load with a deprecation warning: `applications.yaml`, `environment.yaml`, `system.yaml`, `terminal.yaml`, `terminal-optional.yaml`, `desktop.yaml`, `desktop-optional.yaml`, `databases.yaml`, `programming-languages.yaml`, `fonts.yaml`, `shell.yaml`, and platform desktop files such as `gnome.yaml`.

Move application entries to `applications/<category>/<app>.yaml`, environment entries to `environments/`, and setting groups to `system/` or `desktop/`. Remove the old wrapper when writing a per-application or per-environment file. Old init preferences such as `shell: zsh` remain readable but do not define an installable application. The root `dotfiles.yaml` and `security.yaml` files remain supported without a deprecation warning.
